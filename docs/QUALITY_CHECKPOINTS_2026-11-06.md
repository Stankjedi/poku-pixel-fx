## 체크포인트 2 — 작은 자산에 최대 크기 버퍼를 잡던 낭비 제거

기존 CLI와 브라우저 내보내기는 페이지의 현재 사용량에 관계없이
`maxTextureSize × maxTextureSize` 버퍼를 할당했다. RGBA와 RGB float32 발광만
사용하는 2D 2048 페이지는 64 MiB, radiance·occlusion까지 쓰는 페이지는
128 MiB를 처음부터 요구했다.

새 공통 `AtlasPageBuffer`는 packer가 실제 사용한 가로·세로에 맞춰
2의 거듭제곱 크기로 성장하고 최대 크기에서 멈춘다. 아직 한 번도 사용하지 않은
페이지의 픽셀 할당은 0바이트다. 정해진 용량 안의 다음 프레임은 재할당 없이 기록한다.
가로 stride가 바뀔 때 기존 색상·HDR·radiance·occlusion을 행별로 보존하며,
새 occlusion 영역은 중립값 1로 채운다.

예를 들어 32×32 원화 한 장과 양쪽 1px 여백은 34×34 영역을 사용한다.
이때 2D 페이지 용량은 64×64×16 = **65,536바이트(64 KiB)**다.
기존 2048×2048×16 = **67,108,864바이트(64 MiB)**와 비교하면 페이지 버퍼만
1/1024 크기다. 이는 해당 사례의 실제 TypedArray 용량 계산이며,
프로세스 전체 메모리·최대 순간 메모리·렌더 속도 측정값이 아니다.
성장 중에는 이전 버퍼와 새 버퍼가 함께 존재하고, PNG와 ZIP 인코딩은 별도 메모리를 쓴다.

CLI와 Studio는 같은 버퍼를 사용한다. 프레임 rectangle, trim, pivot, 소켓,
프레임 시간, 중복 제거, edge extrusion, 저장 파일의 픽셀은 그대로 유지된다.
Studio는 출력 바이트와 현재 페이지 버퍼 MiB를 따로 표시하고 취소·실패 시
보유한 페이지 버퍼와 출력 Blob 참조를 정리한다.

로컬 검증: 전체 TypeScript·브라우저 번들 빌드 성공, 페이지 성장·RGBA/HDR·3D 조명
복원·경계 확장·중복 제거·프레임 시간·CLI/브라우저 공통 출력 계약 **28개 통과**,
272개 배포 카탈로그 및 준비된 자산과 소스 해시 일치 확인.
Atlas 변경을 그대로 포함한 GPU 후속 head `c3e6d80`에서 Linux·Windows·브라우저·
native wgpu·사이트 빌드의 다섯 CI 작업이 모두 성공했다.
[통합 검증 실행](https://github.com/Stankjedi/poku-pixel-fx/actions/runs/42131521951).
PR #17 자체의 Linux 작업은 선택 GIF 인코더 설치 단계에서 지연됐고 다른 네 작업은 성공했다.
동일 Atlas 코드의 후속 전체 CI와 로컬 검증을 확인한 뒤 #17, #18 순서로 병합했다.

## 체크포인트 3 — GPU 입자 작업량과 반복 할당 감소

이전에는 4,096개 입자를 수용하는 pool에서 128개만 생성해도 4,096개 슬롯 전체를
계산하고 DrawIR로 합성했다. 이제 생존 입자가 차지하는 마지막 슬롯까지만 제출한다.
ID와 슬롯 순서를 유지하므로 내부 빈 슬롯은 남을 수 있으며, GPU 압축 정렬로 출력 순서를
바꾸지 않는다. 생존 수 조회는 O(1), 만료·빈 슬롯 관리는 heap을 사용한다.

- `spawnBatch()`로 한 번에 방출하고 연속 슬롯을 하나의 GPU 업로드로 묶는다.
- 살아 있는 슬롯 사이의 빈 슬롯을 재사용할 때에는 구간별로 전송해 기존 GPU 상태를 보존한다.
- 생존 입자가 없거나 tick·명령이 모두 그대로이면 compute dispatch를 생략한다.
- DrawIR 병합 버퍼의 용량과 bind group을 재사용하고 필요할 때만 다시 할당한다.
- GPU Lab은 생존 수·할당 용량·실제 제출 범위를 구별해 표시한다.

새 4,096-slot pool의 첫 128-particle burst에서 상태 업로드 **128회 → 1회**,
compute workgroup **64개 → 2개**, DrawIR 입자 범위 **4,096 → 128**이다.
GPU Lab의 기본 pool은 512이므로 workgroup은 8→2이다. 이것은 해당 입력의 전송·제출
작업량 비교이며 하드웨어 FPS 측정이 아니다. WGSL의 fixed-tick 물리 계산식은 그대로다.

독립 빌드와 관련 26개 검사를 통과했다. 실제 브라우저용 GPU 검사에도 배치/개별 생성 일치,
비연속 빈 슬롯 재사용, 정확한 만료, idle dispatch 생략을 추가했다.
도형 밀도를 고려한 자동 타일 선택은 이 입자 체크포인트와 구분되는 후속 작업이다.

통합 버전에서 전체 Node 회귀 검사 **820개 통과**, 다섯 CI 작업 모두 성공.
별도 코드 검토에서 Atlas의 stride·채널 복사·dedup·취소 경로와 GPU의 dirty 구간·
만료·buffer/bind group 수명에서 병합을 막을 회귀를 찾지 못했다.

## 체크포인트 4 — 원화에서 최종 픽셀까지 한 번만 샘플링

장비의 소켓 변환을 먼저 픽셀로 굳힌 뒤 캐릭터 배치를 다시 픽셀로 변환하던 경로를
합성 변환 한 번으로 바꿨다. fractional 위치·회전·반전이 섞여도 최종 셀에서 원화 셀을
직접 샘플링한다. RGBA·의미 마스크·HDR 발광은 같은 좌표 변환을 사용한다.
이미 발사된 화살도 발사 시점의 소켓 보정을 최종 배치와 합성해 손의 나중 동작에 끌려가지 않는다.

객체 기준 디더는 장비 자체의 원화 좌표에, 월드·화면 기준 디더는 해당 좌표계에 고정한다.
`space: 'layer'` 편집은 원화 pivot 기준으로 장비에 붙고,
`frameSource: 'layer'`는 캐릭터 cel이 아니라 해당 장비의 독립 cel을 선택한다.
기존 local/socket 편집과 같은 이름의 소켓을 후속 장비가 재정의하던 동작은 유지한다.

독립 빌드와 관련 **52개 검사 통과**. 기본 배치의 기존 참조 캐릭터 4종,
28개 clip의 112개 시점(951,646셀)에서 색상·HDR·의미 마스크·소켓이 이전 결과와 일치했다.
새 회귀 검사는 fractional 변환의 독립 역변환 oracle, 광학 발광,
디더 좌표, 원화 cel 편집, 기존 소켓 편집, 화살의 발사 보정을 다룬다.

## 검증 원칙

기능 동작·출력 일치·성능 계산과 미술적 판단을 구분한다. 소프트웨어 GPU 실행을
물리 GPU의 FPS 향상으로 표현하지 않는다. 새 이펙트의 의미·실루엣·정상 속도 재생은
`EFFECT_INTENT.md`에 따라 별도로 검토한다. 기존 무한 반복형 이펙트와 2D 경로를 유지한다.
