# 효과의 의미, 읽힘, 움직임의 인과

효과는 무엇이 일어났는지 먼저 전달해야 합니다. 픽셀이 선명하고 코드가 정상이어도
회수되는 검이 로켓처럼 보이거나, 물이 갑자기 사라지면 의도가 전달되지 않을 수 있습니다.
이 지침은 효과 제작과 실제 미리보기 평가에 적용합니다. 특정 팔레트, 흰 섬광, 충격파,
파편, 화면 흔들림을 모든 효과에 강제하지 않습니다.

## 1. 그리기 전에 의미와 오독을 적는다

한 문장에 **누가/무엇이 → 무엇을 해서 → 무엇이 달라지는지** 적습니다.
예: "시전자의 손이 바닥의 검을 끌어당겨 다시 쥔다."

- 처음 보는 사람이 알아야 할 의미: 검의 **회수**와 도착점.
- 피해야 할 오독: 검 자체가 불꽃을 뿜으며 하늘로 발사됨.
- 쓰이는 맥락: 캐릭터와 도착점이 보이는 실제 전투 화면, 네이티브 크기와 배경.
- 주된 형태와 시선의 중심: 검의 칼날/손잡이, 손으로 이어지는 궤적.
- 부차적 장식의 역할: 이동을 설명하는 잔상인지, 외부에서 당기는 힘인지 명확히 한다.

"강하고 멋진 초록 이펙트"만으로는 제작 의도가 충분하지 않습니다.
색이나 밝기만 바꿔 공격/회복/방어의 의미가 구분된다고 가정하지 않습니다.

## 2. 물리 모델 또는 과장 규칙을 선택한다

- `physical`: 관찰한 힘·재질·충돌에 맞추려는 표현. 물리 시뮬레이션 인증이 아니다.
- `stylized-physical`: 현실의 인과를 유지하되 속도, 크기, 타이밍 등을 과장한다.
- `magic-with-rules`: 초자연적이지만 힘의 출처, 이동 방향, 반응과 종료 규칙이 읽힌다.
- `symbolic-ui`: 정보·상태 전달이 목적이다. 중력/질량 등이 해당하지 않으면 이유를 적는다.

각 모델에서도 출처, 작용하는 힘, 방향, 재질/무게, 원인→결과, 끝맺음을 작성합니다.
마법이라는 설명은 출처 없는 가속·순간 방향 전환·이유 없는 소멸을 자동으로 정당화하지 않습니다.
그렇다고 모든 마법에 중력이나 실제 에너지 보존을 강제하지도 않습니다.

검 회수 예에서는 손의 신호와 검의 반응을 연결하고, 궤적의 목적지를 유지합니다.
추진을 의도하지 않았다면 검 아래의 지속적인 배기 형태를 피합니다.
도착 전에 방향과 속도가 조정되고 손에 닿은 뒤 남은 흔들림이 잦아들어야 회수로 읽히기 쉽습니다.
이것은 일반화한 제작 예시이며 기존 특정 효과를 검사·수정했다는 뜻은 아닙니다.

## 3. 시간 흐름을 설명한다

준비(`preparation`) → 작용/이동(`action`) → 접촉/반응(`response`) → 종료/루프 연결(`ending`).

각 구간에 실제 시간, 변화, 원인, 관객이 볼 단서를 적습니다. 구간은 겹칠 수 있습니다.
의도서의 전체 시간과 루프 설정은 실제 효과의 `meta.duration`과 `meta.loop`에 맞춥니다.
즉시 반응해야 하는 상태 효과나 지속형 루프에 불필요한 준비/충격을 억지로 넣지 않습니다.
해당하지 않는 단계는 명시적으로 제외하고 이유를 적습니다. 한 프레임의 표식도 시간과
교체/종료 맥락을 설명합니다. "크기와 알파를 0으로 만든다"는 코드 설명만으로 끝맺음을 대신하지 않습니다.

큰 이동 경로와 실루엣을 먼저 확인하고, 의미가 읽힌 뒤 재질과 작은 입자를 더합니다.
방향은 형태·궤적·잔상이 함께 전달해야 합니다. 무게는 가속, 감속, 접촉과 잔류 움직임으로
판단하며, 파티클 수나 히트스톱 수치 하나가 무게를 보증하지 않습니다.

## 4. 실제 결과를 보고 의도와 첫 인상을 따로 기록한다

1. 네이티브 크기의 실제 사용 화면을 정상 속도로 본다.
2. 가능하면 의도를 모르는 별도 관찰자가 이름/설명 없이 무엇으로 보이는지 적는다.
   혼자 또는 제작 에이전트가 보면 `informed-self-review`로 표시한다. 블라인드 검증으로 꾸미지 않는다.
3. 실루엣/휘도 보기에서 형태·초점·앞뒤 관계를 확인한다. 발광만 있는 효과의 빈 실루엣은
   실패 판정이 아니라 진단 한계다. 실제 장면과 함께 판단한다.
4. 준비, 이동, 접촉과 마지막 구간을 재생하고 필요한 프레임을 짚는다. 샘플 시트만으로
   움직임을 봤다고 하지 않는다. 루프는 마지막→처음도 확인한다.
5. 의도한 배경에서 읽힘을 판단하고, 다른 배경 검사는 지원 한계로 기록한다.

각 관찰에 실제 프레임 범위와 구체적 현상을 남깁니다. 예: "12–18프레임에서 손의 신호보다
검 아래 꼬리가 먼저 강해져 자체 추진으로 읽힌다. 꼬리를 줄이고 손과 검의 반응 순서를 수정한다."
수정 후에는 새 출력으로 다시 검토합니다. 고정 횟수를 채우거나 테스트가 통과했다는 이유로
완성 판정을 내리지 않습니다. 가장 큰 오독부터 고칩니다.

## 5. 실행 가능한 작성/검토 도구

Node.js 18+에서 바로 실행하며 추가 설치는 필요 없습니다.

```sh
node tools/effect-intent.mjs init arcane/my-effect
# authoring/arcane/my-effect.intent.json의 빈 필드를 실제 의도로 작성
node tools/effect-intent.mjs validate arcane/my-effect
npm run build
npm run review -- arcane/my-effect
node tools/effect-intent.mjs prepare arcane/my-effect
# 출력된 playback.html과 진단 그림을 실제로 보고,
# intent-review-template-<hash>-<hash>.json을 작성
node tools/effect-intent.mjs record arcane/my-effect /path/to/completed-intent-review.json
node tools/effect-intent.mjs check arcane/my-effect
```

`init`은 기존 의도서를 덮어쓰지 않습니다. `prepare`는 미승인 템플릿만 만들며 실제 검토
기록은 생성하지 않습니다. `record`는 명시적으로 제공한 기록만 저장합니다.
`check`는 현재 의도서·소스·저장된 증거의 일치와 기록의 완결성을 확인합니다.
현재 빌드를 재렌더하지 않으므로 엔진 변경으로 출력이 바뀌었는지는 기존 `share`의
재렌더 identity 검사와 연결해야 합니다. 이 도구는 외부 게시나 소스 실행을 하지 않습니다.

### 자체 평가와 사용자 승인

- `reviewer.kind`는 실제 관찰자인 `human` 또는 `agent`로 정직하게 적습니다.
- `ready`는 그 관찰자의 **시각적으로 확인한 자체 평가**입니다. 사용자 승인과 다릅니다.
- `userApproval.status` 기본값은 `not-recorded`입니다. 사용자 승인을 필요 없이 요구하지 않습니다.
- 사용자 승인을 기록할 때는 해당 버전의 실제 메시지/출처를 근거로 남깁니다. 이름·체크박스만으로
  사람이 봤다고 증명되거나 사용자에게 승인받은 것이 되지는 않습니다.
- 오독이나 인과 문제가 남았으면 `needs-work`, 판단이나 검토가 남았으면 `provisional`로 기록합니다.
- 아직 보지 못한 자료는 `viewed`를 `false`로 남깁니다. 미검토 항목은 `needs-work`와
  구체적 다음 확인 사항으로 기록할 수 있지만, 이 상태로 `ready`를 기록하지 않습니다.
- `not-applicable`은 구체적 이유와 프레임 근거가 필요하며 의미 전달 자체에는 사용할 수 없습니다.

소프트웨어는 문서·시간 범위·파일 해시를 검증합니다. **미학, 물리적 타당성, 실제 열람 여부,
모든 플레이어의 이해도는 자동 판정하지 않습니다.** 실제 관찰 없이 템플릿의 체크를 채우거나
검토 기록을 자동 생성하는 기능은 없습니다. 테스트의 가상 기록은 작품 승인 증거가 아닙니다.

## 기존 workflow 연결 범위

`new/review/share`에 의도서와 실제 검토 기록이 연결되어 있습니다:

- `new`는 빈 의도서를 함께 만듭니다. 원본 효과 코드/팔레트를 자동 개선하지 않습니다.
- `review`는 유효한 의도서를 요구하고 새 증거에 맞는 의도 검토 템플릿을 만듭니다.
- `share`는 기존 시각 검토와 현재 버전의 의도 검토를 모두 확인한 뒤 파일을 준비합니다.
- 일반 `render`, 갤러리, 런타임, 초안 내보내기는 막지 않습니다.
- 기존 효과는 자동 소급 승인하지 않습니다. 완성/공유 대상으로 다시 작업할 때 의도서를 작성합니다.

초기 통합 대상은 기존 2D `review/share`입니다. 3D, 외부 raster clip, 직접 파일 복사는
자동 gate가 없습니다. 해당 제작에도 이 지침을 적용하되, 이 도구가 전 경로를 강제한다고
주장하지 않습니다. GPU 렌더링은 읽힘과 인과를 대신하지 않습니다.

## 기존 엔진 기능을 선택하는 기준

- **회수되는 물체가 자체 추진처럼 보임:** 출발점/목적지와 힘의 출처를 먼저 고정한다.
  `motionTrail`/`drawTrail`로 실제 물체의 과거 위치를 따라 잔상을 만들 수 있지만,
  잔상 자체가 끌어당기는 힘을 증명하지는 않는다. 손이나 시전점의 선행 신호, 물체의
  반응, 도착과 감속을 함께 보여준다. 추진이 아니라면 연속 배기 기둥을 기본 장식으로 넣지 않는다.
- **끝에서 한 점으로 오그라들거나 갑자기 멈춤:** `createTimingCurve`로 위치, 폭, 알파,
  광원을 분리한다. 흩어지거나 진행하며 사라지는 의도라면 이동과 알파를 별개로 작성한다.
  `after: 'continue'`만 바꿔도 공간 경로가 끝점에 고정돼 있으면 해결되지 않는다.
  [TIMING_CURVES.md](TIMING_CURVES.md), [timing-curve.ts](../src/core/timing-curve.ts).
- **접촉보다 먼저 파편이 생기거나 재질 반응이 맞지 않음:** `defineImpactContact2D`의
  시간·위치·법선·재질을 한 번 작성하고 물체 종료와 반응의 공통 기준으로 사용한다.
  접촉 기록은 자동 충돌 판정이나 피해 적용이 아니다. `createGroundImpact`는 흙/돌의
  수평 바닥 반응용이며 물, 금속, 회복 빛에 그대로 붙이지 않는다.
  [IMPACT_INTERACTIONS.md](IMPACT_INTERACTIONS.md), [impact-contact.ts](../src/core/impact-contact.ts).
- **장막·회복·표식에 불필요한 충격파가 붙음:** 정보 전달 또는 지속 상태의 규칙을 선택하고
  필요한 생성/유지/해제 신호만 작성한다. 충돌이 없으면 반응 단계를 제외한 이유를 적는다.
  화려함을 늘리기 전에 보호, 회복, 공격 중 무엇으로 보이는지 실제 사용 크기에서 확인한다.

이 항목은 현재 있는 도구의 선택 지침이다. 기존 효과가 자동으로 수정되거나,
물리적으로 정확한 시뮬레이션과 이해도 검증이 추가됐다는 뜻은 아니다.

검사: `node --test tests/effect-intent.test.mjs`. 기존 검토 도구: [VISUAL_REVIEW.md](VISUAL_REVIEW.md).
